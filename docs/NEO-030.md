# NEO-030 — Signed policy-activation ledger and independently pinned checkpoints (DRAFT)

## Implemented
- `verifyPolicyActivationLedger(entries, externalTrust, initialPolicy, trustedFloor)`: checks up to 256 full NEO-029 Ed25519-signed receipts, one-use operation and policy-change identifiers, hash-chain linkage, contiguous policy versions/digests, and a separately retained count/head rollback floor. Verification-key inputs must be obtained from independently authenticated custody, not from ledger entries.
- `policyActivationEntryHash`: canonical, purpose-separated entry digest helper.
- `policyCheckpointPayload`: purpose-separated checkpoint signing bytes binding witness ID, namespace, count, chain head and active policy version/digest.
- `verifyPolicyActivationCheckpoint`: checks a separately pinned checkpoint-witness Ed25519 key and status, independently retained witness count/head floor, full receipt chain and exact signed checkpoint state. A forged, truncated or forked checkpoint fails closed.
- `reconcileActivationCheckpoint`: compares a supplied, separately observed external policy pin against the verified checkpoint's policy position. Caller must authenticate the checkpoint first.
- Fifteen regression tests cover valid chains, forged custodian/witness signatures, policy gaps, operation replay, rollback, forked floors, revoked keys and invalid input.

## Limits
This module only verifies supplied data. There is **no independently deployed witness**, persistent signed-ledger service, hardware key custody, authenticated clock, physical source independence, real external CAS, or atomic update across ledger and policy store. A signed receipt attests a claimed CAS outcome; it is not proof of durable activation. A signed checkpoint attests a witness's statement, not that the witness was genuinely independent.

The caller must independently pin the initial active policy, the complete custodian verification-key history and the witness's public key/floor. For a real post-write decision, callers must obtain a fresh trusted policy observation and first verify the checkpoint signature; `reconcileActivationCheckpoint` alone does not authenticate its checkpoint argument.

No release, merge, automatic activation, production deployment, key issuance, or external write. All success outputs remain `authorized:false`. GO-13 HOLD / DENY.
