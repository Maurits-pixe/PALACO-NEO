# NEO-043 — Signed audit-custodian key rotation (DRAFT)

## Added
- `custodianRotationPayload` domain-separates signatures binding both old/new Ed25519 public-key fingerprints, fixed custodian identity, namespace, unique rotation ID, full predecessor audit-history head, next checkpoint ID, sequence and pinned OWNER/SECURITY policy digest.
- `verifyCustodianRotation` rechecks explicit old-key and new-key continuity signatures and distinct active OWNER and SECURITY reviews. Reused reviewer/custodian keys, revoked reviewers, changed scope and invalid policy pins fail closed. A valid proof is **evidence only** and always returns `authorized:false`.
- `verifyAuditCheckpointSuccession` accepts optional rotation evidence as a third argument. Existing two-argument usage continues to reject key changes. For a new key at a successor checkpoint, it verifies the full NEO-041 signed checkpoint with the new key and independently verifies a single matching NEO-043 proof from the old key. Rotation sequence, previous audit history head, checkpoint ID and namespace must match. Duplicate rotation IDs, unused proofs and historical key reassignment across custodian IDs are refused.
- Eighteen regression tests cover a valid signed rotation, missing old/new/reviewer signatures, forgery, duplicate reviews, revoked keys, replay, wrong predecessor and checkpoint, rollback and unauthorized key reuse.

## Security limits
No key is generated or rotated by this module and no external trust anchor is changed. This is **read-only evidence validation**. The caller must independently authenticate historical public keys, the review policy pin, the underlying evidence and monotonic history floors. A matching pair of old/new private-key signatures is not proof of human identity, organizational independence, lawful authorization or key non-compromise. A previously compromised old key might falsely co-sign a new key. Safe runtime key rollover, revocation and distribution require a separate operational authorization gate and secure key registry.

Rotation proofs are tied to a single checkpoint transition and not an automatic permission to change future keys. All results remain `authorized:false`. GO-13 HOLD/DENY; no merge, publishing, external writes or deployment.
