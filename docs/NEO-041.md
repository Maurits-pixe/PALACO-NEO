# NEO-041 — Multi-custodian signed audit checkpoints (DRAFT)

## Scope implemented
- `auditCheckpointPayload`: domain-separated Ed25519 statement binds a namespace, checkpoint ID, complete conflict journal count/head, separately trusted predecessor floor and reviewer policy digest to an individual custodian ID.
- `verifyAuditCheckpoint`: re-verifies **all original NEO-040 conflict audit entries**, including underlying NEO-039 histories and original signed fork evidence, against independently pinned reviewer policy and journal floor. Requires 2–16 explicitly pinned ACTIVE custodians with unique IDs and distinct Ed25519 keys, also distinct from review keys. Verifies each original signature and rejects missing, duplicate, mismatched or revoked custodians. Outputs only `AUDIT_CHECKPOINT_VERIFIED_HOLD`, never release.
- `auditCheckpointHash`: deterministic SHA-256 commitment to full signed attestation set and exact checkpoint fields. Order-independent for custodian attestations.
- `inspectAuditCustodianEquivocation`: independently verifies **two individual original signed custodian claims** at the same checkpoint ID, namespace, count, reviewer policy hash and externally pinned predecessor floor. If the same key signed different heads, produces evidence-only `EQUIVOCATION_EVIDENCE_HOLD`. Unlike normal checkpoint verification, it does not require both statements to agree with a validated journal, since the disputed statement may represent a false or alternative branch.
- Nineteen new regression tests cover actual revalidation, tampering, omission, rollback and fork floors, key reuse, revocation, false signatures and same-key contradictory claims.

## Security and operational limits
Two distinct signing keys do **not** prove physical, administrative or legal independence. The entire journal, witness signatures and independently pinned trust roster are supplied to a read-only verifier; the module does not query live storage, synchronize custodian nodes, persist an audit checkpoint, create a replay barrier, guarantee observation freshness, deliver alerts, revoke keys or grant authority.

The equivocation function accepts a valid contradiction between signed assertions from the *same pinned key*, not an authenticated confirmation that two physically stored journal histories existed. External trusted floors, historically valid signing keys, independent storage and protected monotonic anchoring are required to detect erasure and rollback after process restart. A fake floor can conceal erased history. A signed statement is not evidence of a specific human operator's intent.

GO-13 HOLD/DENY. No merge, deployment, external storage writes, automatic dispute closure or authorization; every outcome has `authorized:false`.
