# NEO-013 — Signed dual-review verification under cooperative writer lock (DRAFT)

## Change
The NEO-012 `commitReviewProposal(directory, trustedBefore, evidence)` interface now accepts complete NEO-010 review evidence rather than a precomputed ledger entry.

After the exclusive local lock is acquired and the current ledger is checked against the externally trusted count/head, the method calls `proposeReviewedDecision` to re-check pinned reviewer policy, ACTIVE reviewer status, two distinct Ed25519 signatures (OWNER and SECURITY), registry transitions, and replay against the **actual stored ledger**. It then verifies the appended chain and performs the existing temp-file/fsync/rename/directory-sync sequence.

The untrusted `ledger` and `trustedLedgerHead` fields in `evidence` are overwritten using the locked storage state and separately supplied `trustedBefore`. Old clients passing the NEO-012 raw `{entry,head}` form are rejected.

## Critical limitations
- A hash or provided policy pin **does not** authenticate itself. The application must source `trustedBefore`, reviewer public keys, roles, registry snapshots and `trustedPolicyPin` through authenticated independent custody. This adapter cannot determine that provenance.
- This is a local, cooperative-writer filesystem prototype, not a hostile-process-safe storage engine. Symlink/TOCTOU, cross-process crash, permissions, FS platform semantics and lock cleanup require further hardening.
- Error after rename may represent an uncertain commit. Reconcile with independently trusted before-state and captured proposal; never auto-retry.
- No release, automatic signing, approval authority, deployment, key activation or merge. Every API result retains `authorized:false`; GO-13 HOLD and DENY remain in force.
- A security review and all CI checks are prerequisites for any further release decision.
