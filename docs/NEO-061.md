# NEO-061 — Signed transfer of complete receipt-incident checkpoint evidence (DRAFT)

## Implementation
- `receiptIncidentEvidenceManifest(records)`: enumerates every complete original NEO-060 receipt-incident checkpoint evidence object, including NEO-059 reviewed incidents, NEO-058 receipt checkpoints, NEO-057 transfer succession and all lower archival proof. Binds each checkpoint ID, hash, ordered sequence and a domain-separated SHA-256 commitment to the **entire structured original evidence object**, plus a manifest digest and total count. This creates a manifest, but does not itself certify it.
- `receiptIncidentEvidenceTransferDigest(bundle)`: binds a named transfer ID, namespace, externally authenticated NEO-060 trusted checkpoint floor and complete original manifest.
- `receiptIncidentEvidenceReceiptPayload(bundle,recipientId)`: domain-separated Ed25519 signing payload binds named recipient ID and exact transfer digest.
- `verifyReceiptIncidentEvidenceTransfer(bundle,receipts,trusts,expectedRecipientIds,trustedTransferDigest)`: recomputes full original evidence manifest, rejects missing, extra, reordered or modified source checkpoints; replays **the entire NEO-060 checkpoint chain and NEO-059/058/057/056/055/... original cryptographic proof stack**, refuses false externally retained checkpoint pins, verifies 2–16 distinct ACTIVE recipient identities and valid Ed25519 receipts. Recipients may not reuse NEO-060 checkpoint custodian, NEO-059 OWNER/SECURITY reviewer or disputed NEO-058 custodian public keys. Optional externally retained transfer-digest pin rejects substitution.
- Twenty-six regression tests cover valid single-/multi-checkpoint transfers, missing/additional/reordered checkpoints, nested historical byte changes, forged OWNER and custodian signatures (even after manifest recomputation), signature ordering, revoked/duplicate/forged receipts, transfer scope substitution, shared keys, recipient-role overlap and external pins.

## Important security boundaries
This is a **verification-only module**; it never performs network transfer, remote archive writes, independent storage checks, notifications, incident closure, authority escalation, credential issuance, merge or deployment. A valid cryptographic receipt demonstrates a signing key made a specific statement about a transfer fingerprint, not proof of actual receipt, durable physical custody, data availability, trusted time or real-world organizational independence.

Original source bytes, trust roots, external checkpoint floor and optional transfer digest must be obtained and retained independently. SHA-256 commitments use in-process JSON object serialization: cross-system interoperability requires a separately specified canonical byte encoding and verification procedure. Uniqueness of transfer IDs cannot be guaranteed across independently running processes without a persisted replay ledger. All results set `authorized:false`.
