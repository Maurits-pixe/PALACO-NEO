# NEO-047 — Emergency successor responsibility handoff (DRAFT)

## Implemented
- `responsibilityHandoffPayload`: domain-separated Ed25519 review and successor-acceptance statements bind namespace, ordered hash-chain sequence, unique handoff ID, original NEO-046 incident ID, exact quarantine entry digest and position, original active custodian and key fingerprint, nominated successor identity and key fingerprint, NEO-044 lifecycle digest, NEO-027 policy digest, and the only permissible action `REVIEWED_RESPONSIBILITY_HANDOFF_HOLD`.
- `responsibilityHandoffEntryHash`: deterministic SHA-256 commitment to the precise handoff payload, both independent reviewer signatures and the independent successor responsibility signature.
- `verifyEmergencyResponsibilityHandoffs`: rechecks **all original NEO-046 emergency evidence**, NEO-044 lifecycle evidence and underlying audit checkpoint/history data before inspecting handoffs. Requires one complete signed handoff per supplied emergency quarantine entry in the original order, matching exact original quarantine entry hash and position. OWNER + SECURITY must be distinct ACTIVE reviewers with valid Ed25519 signatures, and the nominated successor must separately sign the handoff using the same key verified under NEO-046. Duplicate incident IDs, handoff IDs and reused successor keys are rejected. A caller-supplied, independently secured monotonic handoff floor detects truncation and forks.
- Twenty regression tests cover valid non-authorizing responsibility statements, forged or missing signatures, duplicate reviewers, altered original quarantine data, historical archive-byte tampering, conflicting context, forbidden successor activation and pinned rollback/fork controls.

## Security and trust limits
A verified responsibility statement means **only cryptographic acknowledgment and review**. This is not a real-world transfer of custody, authorization, new account creation, private key installation, provisioning, key removal or incident closure. The original quarantined key remains in any live external registry until a separate externally authorized execution process revokes it. Neither reviewer signatures nor the successor's possession signature grant access.

The log is verifier-only with no persistence, independent physical custody check, trusted timestamp or externally managed monotonic register. All trust pins, policies, original bytes and historical key identities must be supplied from separately authenticated sources. A signed handoff does not certify uncompromised private keys, legal authority or operational responsibility. In this version an entire supplied quarantine chain must have a corresponding complete handoff chain, which deliberately rejects partial succession evidence rather than silently skipping incidents.

Every result has `authorized:false`. GO-13 HOLD / DENY. No merge, deployment, release, automatic key activation, service access or external writes.
