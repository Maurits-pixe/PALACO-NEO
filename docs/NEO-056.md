# NEO-056 — Incident checkpoint evidence transfer and independent receipts (DRAFT)

## Engineering
- `incidentEvidenceManifest` commits to every complete, ordered original NEO-055 checkpoint evidence object, including original NEO-054 incident reports, signed NEO-053 receipts and upstream proof material. Each item includes checkpoint identity, signed checkpoint hash and SHA-256 digest over its whole structured evidence object; the ordered manifest has its own domain-separated commitment.
- `incidentEvidenceTransferDigest` binds namespace, transfer ID, independently retained checkpoint-floor count/head and the complete manifest using separate domain tags.
- `incidentEvidenceReceiptPayload` binds the named recipient's Ed25519 signature to the exact transfer digest and its namespace/transfer identity.
- `verifyIncidentEvidenceTransfer` validates the complete manifest against the supplied original evidence, including missing, extra, reordered or altered checkpoint files; then replays **the full original NEO-055 checkpoint chain and all NEO-054 and underlying evidence**, and verifies 2–16 ACTIVE, independently keyed recipient signatures. Recipient keys may not reuse NEO-055 checkpoint custodian, NEO-054 reviewer, or disputed NEO-053 custodian keys. Externally pinned transfer hashes are enforced.
- Twenty-five regression cases cover valid single/multi-checkpoint transfers, missing/excess/reordered evidence, original archive bytes and reviewer signature corruption, forged signatures even after manifest recalculation, invalid external checkpoint pins, transfer ID substitution, duplicate or revoked signers, reviewer/custodian key reuse, and deterministic manifests.

## Safety boundaries
This is a **pure verifier**, not an actual transfer or remote archival service. A valid signed receipt means a particular public key verifies a statement about one transfer digest; it does not demonstrate completed physical transfer, durable storage, availability, legal custody, trusted time or organizational independence. No network operation, database write, key activation, account provisioning, incident closure, release or permission is performed.

Every original trust key, monotonic checkpoint floor and externally pinned transfer digest must be separately authenticated. SHA-256 commitments currently use the precise in-process JSON object serialization; portable archival interchange should specify a canonical byte serialization and independent digest checking before interoperability is claimed. A transfer ID alone does not provide cross-process replay protection without an independently persisted registration system.

Every result remains `authorized:false`. GO-13 HOLD/DENY; no merge, deployment or production execution.
