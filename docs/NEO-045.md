# NEO-045 — Signed retired-custodian key revocation register (DRAFT)

## Built
- `custodianRevocationPayload` binds every Ed25519 review statement to namespace, sequence, prior revocation hash, unique revocation ID, custodian ID, SHA-256 Ed25519 key fingerprint, exact prior **retirement sequence**, complete NEO-044 lifecycle digest, audit history count/head, pinned OWNER/SECURITY policy digest and the single allowable action `REVOKE_RETIRED_HOLD`.
- `custodianRevocationEntryHash` commits the exact two reviewer signatures and body to a domain-separated SHA-256 hash.
- `verifyCustodianRevocationJournal` replays complete upstream NEO-044 lifecycle evidence and all NEO-043 rotation signatures, including original NEO-042 audit succession and NEO-040 recovery fork evidence. The register checks that each recorded key is demonstrably retired for the *same* custodian at the *exact* historical sequence, not currently active, not revoked earlier in the supplied register, and reviewed by distinct active OWNER and SECURITY identities. It rejects forgery, missing review, policy substitution, wrong history digest, modified register entries, duplicate IDs/fingerprints, truncation and forked externally pinned register floors.
- Twenty regression tests cover genuine retired-key revocation, active-key refusal, mismatched identity and retirement sequence, unauthorized reactivation action, forged signature, duplicate reviewers, policy pins, source-byte corruption, anti-replay and rollback.

## Guarantees and boundaries
This is **read-only verification** of externally supplied signatures, evidence and trust anchors. It does not create real revocations, write a durable register, execute key revocation at an HSM/service, remove access to live systems, create signatures, release cases, or approve production deployment. Externally retaining an authenticated monotonic `{count,head}` register floor and a trusted NEO-044 lifecycle pin is essential to detect deleted history. A genesis floor cannot establish the absence of pre-existing revocations.

Revocations apply **only to previously retired keys**. Active-key emergency revocation requires an independent fail-closed incident/rotation process rather than an unreviewed or self-authorizing change. Snapshot-bound evidence is deliberately tied to a single lifecycle digest: extending the lifecycle requires a new review process and carefully defined migration policy before importing previous revocation records into a new snapshot. This version provides no such migration, so it must not be interpreted as an operational global revocation service.

All results report `authorized:false`. GO-13 HOLD/DENY; no merge, deployment, automatic revocation or external writes.
