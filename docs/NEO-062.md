# NEO-062 — Signed NEO-061 receipt succession and incident-archive contradictions (DRAFT)

## Implemented
- `receiptIncidentTransferReceiptEntryHash`: a domain-separated SHA-256 commitment binding receipt-register sequence and predecessor, transfer ID, transfer digest, signed recipient statements, trusted Ed25519 key fingerprints, expected-recipient roster, and original NEO-060 checkpoint position.
- `verifyReceiptIncidentTransferReceiptHistory`: re-verifies up to 64 **complete original NEO-061 incident-checkpoint transfer bundles and archive receipt signatures**, including every original NEO-060/059/058/... evidence layer. Refuses duplicate transfer IDs, namespace switching, malformed or tampered chain hashes, altered source evidence, decreased checkpoint height or changed earlier checkpoint/evidence digests. Enforces stable recipient signing-key identity across entries and denies historical reassignment of an Ed25519 key to another recipient ID. A caller-provided externally retained monotonic `{count,head}` floor rejects truncation and forks relative to that previously authenticated floor.
- `inspectReceiptIncidentArchiveContradiction`: independently re-verifies **both full NEO-061 transfers** and identifies when the *same recipient identity and pinned Ed25519 public key* signed distinct transfer digests for the same namespace and transfer ID. Returns `RECEIPT_INCIDENT_ARCHIVE_CONTRADICTION_HOLD` with order-invariant conflict fingerprints. Different IDs, different signing keys, matching transfer statements, or forged receipts do not constitute proven equivocation.
- Twenty-one regressions cover valid one-/two-transfer histories, unchanged-prefix extension, external floor pins, ID replay, forged receipts and changed original archive bytes, recipient-key rotation/reassignment, namespace changes, and genuine versus forged contradictory archive statements.

## Security and operational limits
The module is verification-only. It does **not** create receipt signatures, transfer data, operate an archival service, maintain persistent replay state, contact OWNER/SECURITY, grant permissions, close incidents or deploy code. A signed acknowledgement attests only to the recipient key's statement about a digest, not physical receipt, durable storage, accessibility, legal authority or real-world organizational independence. Distinct public keys alone do not establish independent organizations.

Trusted keys, complete historical data and monotonic receipt-register heads must be authenticated and retained independently. Whole-history deletion is not detectable from a genesis root alone; a durable external floor or anchored ledger is necessary. Local SHA-256 commitments use JSON object serialization; an interoperable wire protocol must standardize a canonical byte format and re-verify decoded bytes. Transfer ID uniqueness is enforced only within the supplied history, not across unconnected processes.

All verifier results explicitly return `authorized:false`; **GO-13 DRAFT / HOLD / DENY**. No merge, deployment, data release or authority issuance.
