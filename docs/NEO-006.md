# NEO-006 — Ed25519 checkpoint attestation (DRAFT)

## Delivered
The verification-only `verifyAttestedCheckpoint(records, envelope, trustedPublicKeyPem, options)` checks canonical checkpoint payloads, Ed25519 signatures, the exact namespace, the audit record chain, and a trusted minimum-count rollback floor.

`checkpointPayload(anchor, namespace)` gives a byte-stable domain-separated serialization for an **external** controlled signer. The application itself has **no private key** and cannot issue or authorize any attestation.

## Boundaries
- A verification result is not operational authority. Every response includes `authorized:false`.
- The public key must be pinned and independently trusted outside the mutable repository / checkpoint storage.
- `minimumCount` must be maintained by trusted monotonic custody; passing zero does not prevent replay of old, otherwise valid signed checkpoints.
- A monotonic count is insufficient to detect a different checkpoint signed at the same count. Production requires trusted (count, head) custody and key rotation/revocation controls.
- This does **not** implement secure key storage, signing, identity, online verification, independent custody, cross-machine durability or fault-injection tests.
- No integration into NEO-004 automatic commit path. No merging, no deployment, no GO-13 release.

Run `npm test` in Node >=20. Cryptographic review remains required.
