## Implementation
- `incidentReceiptCheckpointPayload`: domain-separated Ed25519 signing message binds namespace, checkpoint ID, sequence, preceding checkpoint SHA-256, exact verified NEO-057 register count/head and the witness identity.
- `incidentReceiptCheckpointHash`: deterministic domain-separated SHA-256 commitment to the checkpoint and 2–16 separately named custodian signatures; independent of witness array ordering.
- `verifyIncidentReceiptCheckpointHistory`: independently re-verifies the **complete NEO-057 incident-transfer receipt register** and all NEO-056/055/054/053/... source evidence at each checkpoint; checks prior receipt-entry hash prefix, monotonic receipt height, checkpoint succession, unique checkpoint IDs and independently retained external floor. Requires two or more ACTIVE distinct Ed25519 custodian keys, separate from original archive-recipient and incident-checkpoint custodian keys. Rejects forged, missing, duplicate or revoked signers, unexplained custodian key changes and reuse of historical keys under another identity.
- `inspectIncidentReceiptCheckpointConflict`: checks two contradictory, valid signatures by the **same pinned custodian key** for one checkpoint namespace/ID/sequence/predecessor. Returns `INCIDENT_RECEIPT_CHECKPOINT_CONFLICT_HOLD` and a deterministic forensic digest, without establishing which external history is true.
- Twenty-four regressions exercise valid one-/two-checkpoint verification, full historic archive-byte corruption, forged prior archive receipts, shared and revoked keys, missing signatures, unknown key rotation, conflicting or forged witness statements, trusted-floor rollback/fork and broken hash chains.

## Boundaries and HOLD
This module verifies cryptographic statements and does not issue any signature, store files, provide an append-only hosted service, transfer evidence to external systems, notify owners, release incidents or grant operational authority. Distinct Ed25519 keys do not prove legal, physical or organizational independence. External custody must authenticate and retain the full evidence, public-key rosters and monotonically advancing checkpoint-floor pins; without those, full erasure/replacement of history is not independently detectable.

An empty register at a genesis pin is not evidence that there were no historic records. Conflicting signed claims establish signer-key inconsistency, not which external state is correct. All results explicitly include `authorized:false`. GO-13 DRAFT / HOLD / DENY; no merge or production deployment.
