# NEO-021 — Cross-custody recovery handoff protocol (DRAFT)

## Protocol
- `prepareRecoveryHandoff`: verifies a pinned pre-write challenge-register digest, NEO-018 Ed25519 recovery attestation, exact challenge consumption, and one-step anchor revision. Returns a read-only plan binding the consumed registry and successor anchor.
- `classifyRecoveryHandoff`: compares actual local challenge register with a fresh **independently authenticated** external anchor. Four outcomes: NOT_COMMITTED (both before), PENDING_ANCHOR_CAS (local after, external before), COMMITTED (both after), HOLD (everything else).
- An external custodian should accept a successor anchor *only* through its own authenticated compare-and-swap of the expected before revision+digest, after manual policy review and separately validating the plan. This repo does **not** implement or invoke that CAS.
- If the local register was replaced but the external anchor update was interrupted, classify PENDING_ANCHOR_CAS and refrain from retrying challenge consumption; do not blindly advance custody. If the external anchor advanced while the local registry is old, HOLD.

## Important security boundaries
This is **not** a distributed atomic transaction, external anchor storage, or autonomous recovery engine. The handoff plan is ordinary JSON; anyone who can edit it can fabricate a plan unless the independent custodian authenticates/retains the original plan and verifies its cryptographic provenance. The classifier checks structural consistency but does not validate every historical registry transition from scratch. Never treat PENDING_ANCHOR_CAS as authorization.

No merge, release, background activity or production deployment. All outcomes include `authorized:false`. GO-13 HOLD / DENY.
